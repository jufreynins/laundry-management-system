# Backup and Restore

## What Must Be Backed Up

1. **MySQL database** — all business data (orders, customers, payments, audit logs, etc.)
2. **Private file storage** (`storage/app/private/order-photos/`) — intake photos, referenced by `order_photos.disk_path`
3. **`.env` file** — encryption key (`APP_KEY`), database credentials, mail/SMS/payment provider secrets. Store this separately from database backups (different access controls) since it contains secrets, not business data.

Public assets (`public/build/`) are build artifacts, not data — do not back these up; they are regenerated by `npm run build`.

## Database Backup

Production uses MySQL. Take logical dumps on a schedule (daily minimum; hourly if transaction volume is high):

```bash
mysqldump --single-transaction --routines --triggers \
  -u <user> -p <database_name> | gzip > backup_$(date +%Y%m%d_%H%M%S).sql.gz
```

`--single-transaction` ensures a consistent snapshot without locking tables (safe for InnoDB, which all tables in this schema use by default).

Store backups off-server (S3, separate backup host, etc.) with retention matching the business's data-retention policy. Encrypt backups at rest given they contain customer PII (name, phone, address) and financial records.

## File Storage Backup

```bash
tar -czf photos_backup_$(date +%Y%m%d).tar.gz storage/app/private/order-photos/
```

Sync this to the same off-server location as database backups, on the same schedule. If a cloud disk (S3) is configured for the `local` filesystem disk in production (see `config/filesystems.php`), the cloud provider's own durability/versioning may suffice instead of a separate file backup step — confirm this explicitly rather than assuming.

## Restore Procedure

1. **Provision** a fresh database and application environment matching the target Laravel/PHP version (see `CLAUDE.md` for stack versions).
2. **Restore `.env`** first — the encrypted `APP_KEY` must match the one used when data was encrypted/backed up, or encrypted columns (business settings marked `encrypted`) become unreadable.
3. **Restore the database**:
   ```bash
   gunzip < backup_YYYYMMDD_HHMMSS.sql.gz | mysql -u <user> -p <database_name>
   ```
4. **Restore file storage**: extract the photos archive into `storage/app/private/order-photos/`, preserving the `{order_id}/` subdirectory structure that `order_photos.disk_path` references.
5. **Run pending migrations** if the restored dump predates the current schema:
   ```bash
   php artisan migrate --force
   ```
6. **Verify**:
   - Log in as an Owner account and confirm the dashboard loads with expected order counts.
   - Open a recent order with an intake photo and confirm the photo renders (validates file storage path integrity).
   - Check `docs/PROJECT_STATUS.md` "Latest successful test command" and run it against the restored environment.
7. **Rotate secrets** if the restore followed a suspected compromise (new `APP_KEY` requires re-encrypting any `encrypted` business settings; new payment/SMS provider credentials if those may have leaked).

## What Restore Does NOT Recover

- Anything written after the last backup (the RPO — recovery point objective — equals your backup frequency; choose it based on acceptable data loss for a laundry business, typically no more than 24 hours of order/payment data).
- Audit logs are themselves data in the same database dump — restoring an old backup means losing audit trail entries created after that backup, same as any other table. There is no separate immutable audit log store in this MVP.

## Testing Restores

A backup that has never been restored is unverified. Periodically (quarterly minimum) perform a full restore into a staging environment and run the verification steps above. Note the date of the last verified restore test in `docs/PROJECT_STATUS.md`.
